# abstractions/modules/agents/shield/

## Local Contract

- An engine is a `Shield.Engine` module registered in `hub/lib/shield/engine.ex`, which documents the effects the Agent performs. The only engine is `Shield.Keel`, which holds keel's model and drives the keel driver process. `Agent`, `Manager`, `Connection`, and `Protocol` stay engine-neutral; engine-specific behavior, state, and error codes belong in the engine and the modules under it (`hub/lib/shield/keel/`). `hub/test/engine_neutrality_test.exs` checks that their compiled code names no module other than each other, `Shield.Engine`, and `Shield.Listener`; it cannot see engine-specific strings such as error codes.
- The neutral core owns process lifetime, connections, and the writer of each agent; it never interprets an engine's records or state. An engine module may own its harness's model: keel's model (state, sequence, and who may run what) is `Shield.Keel`'s, and Pi's meaning and the extensions' code belong to the keel driver (`keel/`).
- `contracts/` holds the TypeSpec sources of the keel contract (driver, model, and screens) and of the management contract (the hub's envelope and requests). The generated JSON Schemas and TypeScript modules in `contracts/generated/` are committed and written only by `just shield-contracts`; the `contracts` build case fails when they are stale. `contracts/cases.json` holds values both languages' validators must judge alike, and `contracts/state.json` the state the model publishes before any extension declares, which the screen tests start from and the hub tests check against the model. The keel contract is validated by every receiver at run time. The management contract is checked against real exchanges only: the neutral core keeps its own parsing and limits and takes no schema validator.
- The management CLI is `client/shield.cr`, a native executable built with Crystal's standard library alone; the screen's client stays TypeScript (`client/protocol.ts`, `client/paths.ts`). Revisit the CLI's language if it grows beyond managing the hub.
- SHIELD's supported platforms are defined in `platforms.nix`; packages and build cases read that declaration without evaluating one another. The current Darwin restriction reflects `/usr/bin/lockf` and socket path sizing. When changing availability, evaluate Linux packages and checks as well as Darwin.
- Tests never touch the user's SHIELD or keel directories, sockets, or credentials: they use temporary `XDG_CONFIG_HOME`/`XDG_STATE_HOME`, an explicit `--socket`, and the faux provider.

## Validation

- Hub logic, keel's model included: in `hub/`, run `MIX_ENV=test mix test --no-start`. `nix fmt` formats the hub with treefmt's `mix format`. `hub/test/fixtures/projection.json` holds the projection the TypeScript model gave before the model moved to Elixir; it records how it was captured and is not regenerated from the Elixir model.
- From this directory, run `bun node_modules/typescript/bin/tsc -p .` and `bun test`. From the repository root, run the development shell's `oxlint --config .oxlintrc.json --deny-warnings abstractions/modules/agents/shield`. The type check and lint cover this entire Bun project, including `build.ts`, the screen's client, the generated contract modules, and process fixtures.
- The CLI: `crystal spec client/spec` from this directory; the package build runs it too.
- In `keel/`, `node check-ui.ts --project ../tsconfig.json extensions/*.ts fixtures/*.ts` checks for unsupported `ctx.ui` use; it needs Node, not Bun.
- `nix build .#checks.aarch64-darwin.module-shield` runs the inline fixture checks, including contract freshness, type/lint/UI validation, and process, socket, management-contract, and real driver behavior through the packaged executables. The process case includes a 60-second startup deadline, so it is slow. Package builds retain Bun, Mix, and Crystal tests.
