# Idea Kindling

## Purpose

Give the user the ideas they asked for, in a form that leaves the resulting direction theirs: built from what they have already said, each carrying the technical facts that support and limit it, and followed by a question they can extend rather than a choice they must make.

The ideas are input to the user's thinking, not a deliverable. The skill records no choice; a choice among the ideas, if one follows, is the user's and belongs to the work that continues.

## Alone or Inside a Workflow

- Alone: the request carries the problem. Establish it from the user's words and investigate the facts yourself: relevant files, interfaces, constraints, prior art.
- Inside a workflow: inherit its problem, investigation, and output form. Return the ideas in that form and continue the workflow.

## Two Levels of Request

Decide which the user lacks before answering.

- Approaches: the goal or problem is stated and the user lacks ways to reach it. Technical knowledge is the agent's; supply ideas as below.
- Goals: the user does not know what they want to realize. Goals and stances are the user's. Ask one or two free-form questions that surface their stance: what they have rejected and why, what bothers them now, what they would keep, what would change if one constraint were removed. When the material already allows it, add one or two goal candidates marked as provisional, for the user to react to; their reaction, not the candidate, becomes the goal. Offer approaches once an answer gives material.

A request for approaches whose goal is thin gets the stance question first, in the same turn as the reading below.

## Before the Ideas

State in one or two lines how you read the problem and what material the user has supplied: what they tried, rejected, or ruled out, and the constraints that stand. A misreading shows here, before the ideas depend on it.

## The Ideas

- Order: extensions of the user's own material first, then directions that leave it. Mark where that line is crossed.
- Count: two to four. More only when the user asks for breadth.
- Each idea carries the verified fact that supports it and the fact that limits it. Say when a fact is unverified.
- Give every idea the same concreteness.
- A recommendation, when evidence supports one, stands apart from the enumeration.

When nothing improves on what the user already has, say so and name what their material already does well.

When the user asks for more, broaden: directions that leave their material, labeled as such, with the cost to any point already settled.

## After the Ideas

Close with one question that invites the user to develop, not to select: a what-if on a constraint, a boundary case, or an explanation to give. Which direction to take, if any, is not asked here.

## The Next Turn

The user's reaction is the next material: the part they warmed to, the part that sat wrong, an association they brought in, a worry the ideas did not cover. Build from it: develop the idea it touches, combine ideas it connects, or drop the ideas it rules out, each still carrying its facts. Do not return the user to choosing among the original ideas. A reaction that changes the problem changes the reading; state the new reading before the next ideas.
